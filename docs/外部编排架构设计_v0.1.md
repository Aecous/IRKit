# 外部编排架构设计 v0.1

> 日期：2026-11-13
> 配套文档：《架构设计文档 v0.3》
> 核心决定：使用 Python 实现外部 Orchestrator；Claude Code/Pi 是可替换 Worker，不承担案件总控。
> 采集范围：日志包、SSH、云凭据按需启用；镜像/挂载盘采集暂列待定。

---

## 1. 为什么需要外部编排器

如果完全依靠 Claude Code 会话驱动，会遇到几个结构性问题：

- 会话结束后，任务、证据和调查进度需要额外整理。
- 多个会话并行时，缺少统一的任务认领、结果合并和冲突检查。
- 长时间入库、云日志拉取等确定性任务不适合由模型自由控制。
- 超时、重试、预算、取消和断点恢复无法仅通过提示词可靠实现。
- 更换 Worker 底座时，案件状态不应随之丢失。

因此，**外部 Orchestrator 是系统控制面，Claude Code 只是其中一种执行后端**。

## 2. 参考 Cairn 的方式

### 2.1 借鉴的工程机制

| Cairn 机制 | 本系统的对应设计 |
|---|---|
| Server 保存项目状态 | Case API + Case Repository，保存 Brief、Fact、FactLink、TraceTask |
| Dispatcher 是主要状态写入者 | Scheduler/Coordinator 统一提交任务结果和状态变更 |
| Worker 无状态 | Worker 只接收任务包、调用工具、返回结构化结果 |
| Worker Driver | Claude Code、Pi、Mock 等适配器实现统一接口 |
| 任务认领、心跳、超时 | Task Lease、Heartbeat、Timeout、Retry |
| 超时后的 conclude | 收尾时只提交已经获得证据支持的观察，不继续扩展调查 |
| Prompt 文件分组 | 按任务类型维护版本化 Prompt |
| local/container 运行后端 | 第一版本地子进程，容器作为后续隔离选项 |
| Mock Worker 和端到端测试 | 无模型测试调度、失败恢复和状态一致性 |

### 2.2 不沿用的部分

- 不把 Cairn 的 Fact/Intent 正向探索图作为调查数据模型。
- 不让 Bootstrap 尝试一次完成整个调查。
- 不让模型通过一次主观判断直接把案件标记为完成。
- 不沿用渗透 Worker 的宽松权限和联网方式。
- 在许可证问题未明确前，不直接复制其代码；参考机制，独立实现。

### 2.3 Bootstrap 的替换方式

Cairn 的 Bootstrap 在本系统中拆成三个步骤：

```text
Acquire（可选，确定性采集）
    → Ingest + Profile（必选，确定性入库与数据体检）
    → Anchor Proposal（可选，Agent 提议初始锚点，由分析师确认）
```

它不能直接结束案件。后续进入 TraceTask 驱动的倒叙调查。

## 3. 总体形态：本地模块化单体

第一版不拆微服务，不引入 Celery、Redis 或消息队列。一个 Python 进程包含控制面和调度面，通过清晰的内部模块边界保留以后拆分的可能。

```text
┌──────────────────────────────────────────────────────────────┐
│ 分析师：CLI / Claude Code 协同入口 / 后续 Web UI               │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│ Python Orchestrator                                           │
│                                                              │
│  FastAPI Case API                                             │
│    │                                                         │
│    ├── Case Service ──────── SQLite Case DB                   │
│    ├── Data Gateway ──────── DuckDB Event DB                  │
│    ├── Evidence Store ────── 原始文件、Manifest、任务产物       │
│    ├── Scheduler ─────────── 任务生成、去重、优先级、预算        │
│    ├── Task Runner ───────── 子进程、心跳、取消、超时、重试      │
│    ├── Result Verifier ───── 证据与结构校验                    │
│    └── Report Renderer ───── Markdown                         │
│                            │                                 │
│              ┌─────────────┴──────────────┐                  │
│              ▼                            ▼                  │
│      Deterministic Runner          Worker Adapter             │
│      采集/解析/入库/渲染            Claude Code / Pi / Mock      │
└───────────────────────────────────────┬──────────────────────┘
                                        │ 受限工具调用
                                        ▼
                              MCP/HTTP Tool Gateway
                              不直接向 Worker 开放数据库文件
```

### 3.1 两个执行通道

**确定性任务通道**处理：

- 场景采集。
- 格式识别、日志解析、DuckDB 写入。
- 数据覆盖统计。
- 命名指标计算。
- Markdown 渲染。

这些任务不调用 LLM。

**Agent 任务通道**处理：

- 锚点建议。
- 单个 TraceTask 的调查。
- 证据核验和语义研判。
- 无法由固定规则生成时的下一步建议。
- 报告叙述草稿。

## 4. 核心模块

### 4.1 Case API

对分析师和外部界面提供稳定接口：

```text
POST   /cases
GET    /cases/{case_id}
POST   /cases/{case_id}/briefs
POST   /cases/{case_id}/sources
POST   /cases/{case_id}/ingest
GET    /cases/{case_id}/board
POST   /cases/{case_id}/facts
POST   /cases/{case_id}/facts/{fact_id}/review
GET    /cases/{case_id}/tasks
POST   /cases/{case_id}/tasks/{task_id}/cancel
POST   /cases/{case_id}/reports/render
```

内部任务认领和结果提交不暴露为 Worker 自由调用的通用接口，而由 Task Runner 处理。

### 4.2 Case Repository

SQLite 保存：

- Case、Brief。
- Fact、FactLink。
- TraceTask、TaskAttempt。
- Coverage、Gap。
- WorkerRun、AuditEvent。
- ReportRevision。

所有重要对象带 `revision`，任务结果提交时检查其依赖版本，避免把旧结果覆盖到新状态上。

### 4.3 Data Gateway

所有数据库访问都经过 Data Gateway：

- Worker 不直接打开 DuckDB 文件。
- 入库由单一 Data Writer 负责。
- 查询接口限制为只读，带超时、返回行数和敏感字段策略。
- 增量入库和并行查询由 Gateway 协调，避免多个进程同时写 DuckDB。
- 事件证据查询与 SQLite 中的 Fact 引用使用同一案件命名空间。

解析器只负责产出统一事件批次，不各自建立数据库连接。

### 4.4 Scheduler

Scheduler 不负责“自由思考”，主要负责：

1. 找出可运行任务。
2. 按优先级和预算排序。
3. 原子认领任务并生成 lease。
4. 选择确定性 Runner 或 Worker Adapter。
5. 处理超时、重试、取消和结果提交。
6. 根据新状态生成后继任务。

任务生成优先使用固定规则。只有规则无法决定下一步时，才创建一次可选的 `PLAN` Agent 任务。

### 4.5 Task Runner

统一运行两类任务：

- Python 函数或独立解析进程。
- Headless Agent CLI/SDK 子进程。

负责：

- 创建任务工作目录。
- 注入最小权限工具配置。
- 维护心跳和进度。
- 捕获标准输出、错误和结构化结果。
- 超时后请求 Worker 收尾；收尾失败则保存已有工具审计。
- 支持人工取消和案件暂停。

## 5. 任务模型

### 5.1 系统任务

| 类型 | 是否调用模型 | 说明 |
|---|---|---|
| `ACQUIRE` | 否 | 按所选场景采集原始数据 |
| `INGEST` | 否 | 解析并写入统一事件库 |
| `PROFILE` | 否 | 生成覆盖范围、解析错误和缺口 |
| `VERIFY_QUERY` | 否 | 重放指定查询或计算命名指标 |
| `RENDER_REPORT` | 否 | 从案件状态生成 Markdown |

### 5.2 调查任务

| 类型 | 方向 | 说明 |
|---|---|---|
| `ANCHOR_PROPOSAL` | — | 根据 Brief 和数据概览建议锚点 |
| `TRACE` | backward | 寻找当前 Fact 的前置节点 |
| `TRACE` | forward | 从入口或早期节点补全后续行为 |
| `TRACE` | lateral | 检查关键实体在其他范围内的活动 |
| `VERIFY` | verify | 核实事件结果、证据强度和节点定性 |
| `PLAN` | — | 固定规则无法推进时，建议少量后续任务 |
| `REPORT_DRAFT` | — | 基于已确认状态撰写叙述草稿 |

`PLAN` 不是 Cairn 那种不断读取全图、自由决定整个系统方向的常驻循环，只是一个有边界、可取消、输出受约束的任务类型。

### 5.3 任务状态机

```text
pending
   │ 原子认领
   ▼
leased ──▶ running ──▶ verifying ──▶ succeeded
  │           │             │
  │           │             ├──▶ retry_wait ──▶ pending
  │           │             └──▶ failed
  │           ├──▶ blocked_waiting_human
  │           ├──▶ cancelled
  │           └──▶ timeout ──▶ concluding ──▶ verifying/failed
  │
  └── lease 过期且无有效心跳 ──▶ pending（受最大尝试次数限制）
```

每次运行生成独立 `TaskAttempt`，结果提交必须幂等，防止超时重试造成重复 Fact。

## 6. 调查任务如何自动生成

### 6.1 事件驱动，而不是持续空转

以下变化会触发任务规划：

- 新 Brief 被确认或否定。
- 新数据源完成 Ingest/Profile。
- 新 Fact 被确认。
- Fact 被修订或推翻。
- 新 Gap 或人工回答出现。

### 6.2 规则优先

示例规则：

- 一个已确认 Fact 尚无前置节点，且相关数据源覆盖允许继续调查，则生成 backward TraceTask。
- 一个已确认入口存在未调查的下游范围，则生成 forward TraceTask。
- 一个关键实体尚未在指定范围内排查，则生成 lateral TraceTask。
- 一个候选 Fact 的证据或结果等级存在疑问，则生成 VerifyTask。
- Fact 被推翻时，将依赖它的任务和结论标记为需要复核，而不是继续沿用。

任务使用去重键：

```text
case_id + task_type + subject_id + normalized_scope_hash
```

避免同一问题被反复派发。

### 6.3 优先级建议

1. 分析师明确指定的任务。
2. 新数据入库和证据保全。
3. 关键结论核验。
4. 从高置信度 Fact 出发的 backward。
5. 关键实体的 lateral。
6. 已确认入口的 forward。
7. 低置信度假设探索。

第一版建议每案最多并行 1–2 个 Agent 任务，避免结果量和冲突快速增长。

## 7. Worker 协议

### 7.1 统一适配器

```python
class WorkerAdapter(Protocol):
    def check(self) -> HealthResult: ...
    def start(self, task: TaskContext) -> WorkerHandle: ...
    def conclude(self, handle: WorkerHandle) -> WorkerResult: ...
    def cancel(self, handle: WorkerHandle) -> None: ...
```

适配器实现：

- `ClaudeCodeAdapter`：第一版主要后端。
- `MockAdapter`：测试调度和故障恢复，不依赖真实模型。
- `PiAdapter`：后续需要本地模型时增加。

具体 CLI 参数和会话机制封装在适配器内，不进入调度器逻辑。不使用绕过权限检查的运行参数。

### 7.2 任务输入包

Worker 不读取整张图，只获得完成当前任务所需的最小上下文：

```json
{
  "task_id": "T-...",
  "case_revision": 42,
  "task_type": "TRACE",
  "direction": "backward",
  "question": "寻找当前节点可证实的前置事件",
  "current_fact": {},
  "relevant_briefs": [],
  "nearby_facts": [],
  "known_gaps": [],
  "scope": {},
  "tool_instructions": {}
}
```

### 7.3 任务输出

```json
{
  "task_id": "T-...",
  "status": "done",
  "observations": [],
  "candidate_facts": [],
  "candidate_links": [],
  "coverage": [],
  "gaps": [],
  "suggested_tasks": [],
  "summary": ""
}
```

Worker 只能提交候选结果，不能直接确认入口、修改 Brief、确认报告或结束案件。

## 8. 结果校验与提交

Result Verifier 至少检查：

1. JSON 结构、任务 ID 和本次运行是否匹配。
2. 所有 `event_id` 是否存在且属于当前案件。
3. Fact 的时间、主体、对象是否与证据相容。
4. 结论是否超出声明的数据覆盖范围。
5. 是否违反已确认 Brief 或分析师裁定。
6. 关系类型是否与证据强度相符。
7. 是否重复提交已有 Fact 或 Task。
8. 任务创建时的依赖版本是否已经失效。

处理策略：

- 直接观察且证据充分的内容可以成为已验证观察。
- 语义判断、入口和影响范围默认仍需分析师确认。
- 校验失败可把错误反馈给同一 Worker 修正一次；仍失败则结束该次尝试。
- 超时收尾只接受已有证据支持的内容，不允许为了“补完整”而新增无证据推断。

提交后统一推进 `case_revision`，再触发后继任务规划。

## 9. 场景 Skill 在外部编排中的位置

场景不应只写成提示词 Skill。建议分两层：

### Python 采集插件

负责可测试、可重试的实际工作：

```text
log_bundle
ssh_instance       按授权启用
cloud_credential   按授权启用
mounted_image      待定，暂不实现
```

插件只输出原始文件和 Manifest，不直接修改调查状态。

### Claude Skill

负责：

- 帮助分析师选择合适的场景。
- 收集必要参数和授权边界。
- 解释采集结果和失败原因。
- 指导使用对应工具。

**核心流程由 Python Orchestrator 控制，不依赖模型是否严格阅读了 Skill。**

## 10. 建议技术栈

- Python 3.12。
- `uv`：项目管理。
- FastAPI + Uvicorn：本地 Case API。
- Pydantic：领域模型和 Worker 输出协议。
- Typer：管理 CLI。
- SQLite（WAL）：案件状态。

## 12. 调度主循环示意

```python
while running:
    reap_expired_leases()
    reap_finished_processes()
    ingest_new_sources()
    plan_from_state_changes()

    for task in scheduler.next_runnable_tasks():
        if not budget_allows(task):
            break
        attempt = task_repository.lease(task)
        runner.start(attempt)

    wait_for_event_or_interval()
```

真实实现应采用事件等待与短周期兜底结合，避免固定高频轮询。调度器只处理控制逻辑，不在主循环中执行大文件解析或模型调用。

## 13. 完成与暂停

案件不因“暂时没有任务”自动完成：

```text
READY → INVESTIGATING → WAITING_REVIEW → COMPLETED
             │  │                            │
             │  └── WAITING_HUMAN ───────────┘
             └────── PAUSED / CANCELLED
```

- `WAITING_REVIEW`：当前没有可运行任务，等待分析师审阅。
- `WAITING_HUMAN`：存在必须人工回答的问题。
- 新证据、新 Brief 或结论推翻可重新打开案件。
- 最终完成必须由分析师明确确认。

## 14. 实施顺序

### O0：无模型编排骨架

- Case API、SQLite、DuckDB Gateway。
- 系统任务和 Task Lease。
- Mock Worker。
- 日志包采集与某业务系统 nginx 入库。
- Markdown 渲染。

先证明调度、重试、取消和状态一致性可靠。

### O1：接入 Claude Code Worker

- 单任务输入包和结构化输出。
- TRACE backward/forward/lateral。
- Verifier 和人工 Fact 审核。
- 工具审计和任务预算。

### O2：倒叙任务生成

- 基于状态变化的规则规划。
- 任务去重、结论修订和依赖复核。
- 可选 PLAN 任务。

### O3：采集扩展与受控并行

- SSH、云凭据插件。
- 每案 1–2 个并行 Worker。
- 心跳收尾、断点恢复和容器隔离。
- Pi 适配器按离线需求接入。

## 15. 第一版的验收重点

- 模型不可用或 Worker 崩溃时，已入库数据和已确认 Fact 不丢失。
- 同一任务重试不会产生重复节点。
- 新数据可以增量入库，Worker 不直接写数据库。
- 一个 Fact 的每个证据引用均可回查。
- 推翻关键 Fact 后，相关任务和结论能标记为待复核。
- 并行 Worker 的结果统一进入同一案件状态。
- 报告可以完全从案件状态重新生成。
- 镜像/挂载盘采集不影响当前架构，未来可作为新的 Acquisition 插件加入。
