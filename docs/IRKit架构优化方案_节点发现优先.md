# IRKit 架构优化方案：节点发现优先，分析后置

> 日期：2026-11-16
> 依据：IRKit 源码（`events.py`、`board.py`、`integrity.py`、`verification.py`、`templates.py`、`report_template.py`）与过往调查复盘。
> 目标：在保留现有证据纪律的前提下，提高节点召回、缩短时间，并让时间线和攻击路径成为一等产物。

---

## 1. 问题的结构性原因

### 1.1 一张卡片同时承担了太多职责

现在的事件卡同时是：

1. **发现记录**：这里有一个可疑行为；
2. **定性结论**：它是什么、成功没有、影响多大（claims、observed_effects、potential_impacts）；
3. **工作义务**：upstream / downstream 两个问题，默认 critical，未处理就阻断结案；
4. **报告单元**：每张卡都要在 `review_delivery` 中逐项复核。

所以每新增一个节点，都要**当场完成全部定性**，并**背上补证和复核义务**。过往调查中，卡片登记、修订与复核占用了较多的工具调用。

这里的激励是反的：**新增一个节点很贵，修改已有节点相对便宜**，于是 Agent 倾向于少建卡、反复打磨已有的卡。漏掉命令执行阶段，本质上是广度不够。

### 1.2 子 Agent 的任务是“深挖一个问题”，不是“找全节点”

`ir-investigate` 的定位是“围绕明确问题取证”，提示词要求“初轮每个调查尽量保留 1–3 个高价值事件”，并在同一个任务里完成前因、后果、来源、正文、解码、统计口径等全部核查。这天然是深度优先的。

而应急调查的第一要务是**不漏掉节点**。深度可以后补，漏掉的节点在报告里根本不会出现。

### 1.3 为什么不能简单地“先全部发现，再全部分析”

客观上，发现和分析并不能完全分开：

- 很多节点是**顺着已有节点找邻居**发现的（同一会话之后做了什么、同一账号之前从哪来）。这一步本身就是发现。
- 节点的大致结果（例如请求是否报错、登录是否成功）往往就在同一行日志里。拿到它几乎没有成本，而且决定了节点值不值得继续追。

所以合理的切分是：

| 归入“发现” | 归入“分析” |
|---|---|
| 找到节点、找一跳邻居、读同一行可见的结果 | 证明成功与否、跨日志核实结果、评估影响、来源归属、统计口径 |
| 广度优先、成本低、批量提交 | 深度优先、成本高、只对关键节点做 |

## 2. 目标架构

```text
                  ┌──────────────── 数据准备 ────────────────┐
日志 ──► 入库 ──► │ 系统分组 + 确定性摸底（信号）              │
                  └──────────────────┬──────────────────────┘
                                     │ signals（候选，未研判）
                  ┌──────────────────▼──────────────────────┐
                  │ 发现：ir-discover（广度，多个并行）        │
                  │ 信号研判 → 节点；一跳邻居 → 更多节点        │
                  └──────────────────┬──────────────────────┘
                                     │ nodes（轻量，按时间可排序）
                  ┌──────────────────▼──────────────────────┐
                  │ 组装（确定性代码）                         │
                  │ 时间线排序 → 分链 → 阶段断档/空白时段检测   │──► 缺口问题 ──┐
                  └──────────────────┬──────────────────────┘                │
                                     │ chains                    回到发现补节点 ◄┘
                  ┌──────────────────▼──────────────────────┐
                  │ 分析：ir-analyze（深度，按链分派）          │
                  │ 关键节点 → 事件卡：结果核实、影响、来源归属 │
                  └──────────────────┬──────────────────────┘
                                     │ cards（重，只覆盖关键节点）
                  ┌──────────────────▼──────────────────────┐
                  │ 综合：ir-synthesize                        │
                  │ 先确认路径，再复核路径上的卡片，出报告       │
                  └─────────────────────────────────────────┘
```

核心变化：**黑板从“一种重卡片”变成“信号 → 节点 → 事件卡”三层**。时间线和攻击路径由节点生成，事件卡只为关键节点提供深度结论。

## 3. 黑板机制改造

### 3.1 三层对象

| 层 | 是什么 | 谁产生 | 成本 | 是否产生义务 |
|---|---|---|---|---|
| **Signal 信号** | 确定性摸底给出的候选，例如“某对象被写入”“某异常类型首次出现”“某时段写请求激增” | 工具（无模型） | 极低 | 否，只计入覆盖账本 |
| **Node 节点** | 一个已确认存在的行为，钉在原始行上，带时间、主体、动作、对象和同行可见的结果 | 发现 Agent | 低，可批量提交 | 否 |
| **Card 事件卡** | 对一个或一组节点的深度结论：是否成功、造成什么、来源可信度、统计口径 | 分析 Agent | 高（沿用现有契约） | 是，但只针对路径上的关键卡 |

现有的 card、check、link、claims 校验、修订历史全部保留。新增 signal 和 node 两种 kind，存储仍然使用同一张 `objects` 表。

### 3.2 节点（Node）的最小字段

```text
node_id
key_time            关键时刻（带时区的 ISO 时间；未知则 time_basis=unknown）
time_basis          recorded / inferred / unknown
system              系统（由数据准备阶段的系统分组给出，如 ucenter、风险策略系统）
actor               主体：来源地址 / 账号 / 会话 / 票据（取实际字段，可多个）
action              动作：方法+路径、事件类型、日志动作等
object              作用对象：账号、配置键、菜单、文件、角色等（可空）
observed_result     同一行可见的结果：状态码、成功/失败消息、异常类型（原样，不做推断）
stage_hint          阶段猜测：recon / access / credential / execution / persistence / lateral / collection / exfil / impact / unknown
refs                1–3 个原始行引用（必填）
signal_ids          由哪些信号引出（可空）
from_node_id        由哪个节点顺藤摸瓜找到（可空，用于还原调查路径）
dedupe_key          system + actor + action + object + 时间桶，用于自动去重/合并
```

关键设计：

1. **字段由工具从原始行自动抽取。** 模型只提供 `refs` 和一个简短标签，时间、方法、路径、状态、来源由工具从数据行读出。这样消除了“时间/方法/状态必须来自同一行”这一类报错，节点提交基本不会失败。
2. **批量提交**：`submit_nodes([...])` 一次可以提交几十个节点。
3. **没有 upstream / downstream 义务**，节点本身不阻断结案。
4. **重复自动合并**：相同 `dedupe_key` 的节点合并计数，并保留首次和末次时间，不报错。
5. **节点不可修订，只能补充。** 节点是观察，不是结论；结论的变化发生在事件卡上。这样节点永远不会触发失效连锁。

### 3.3 事件卡改为“节点的深度结论”

- 事件卡新增 `node_ids`，表示这张卡解释了哪些节点。
- 卡片的 claims、来源、统计契约保持不变。
- **upstream / downstream 问题改为可选**，并且只对路径上的卡默认开启。是否发生前因或后果，由路径断档检测（见第 4 节）统一生成，不再每张卡各自背两个义务。
- `stage`、`chains`、`outcome` 作为路径标注，**不计入事实哈希**，修改它们不会让补证失效。

### 3.4 覆盖账本

按“系统 × 小时”维护一张聚合表，每格记录：

- 原始记录数；
- 信号数，以及其中已被节点或检查解释的数量；
- 节点数、事件卡数。

结案门槛新增一条：**存在“有高价值信号、但无节点也无检查”的时段时，不能出终稿**，或者必须在报告中列为“未调查时段”。例如某个时段存在业务写入信号，但未被任何调查任务覆盖。

## 4. 组装：时间线与攻击路径由程序生成

这一层完全是确定性代码，不调用模型。

### 4.1 时间线

全部节点按 `key_time` 排序，跨系统统一时区；`time_basis=unknown` 的节点单列，不参与排序。时间线上每一行都是一个节点，显示系统、主体、动作、对象、同行结果和阶段；已有事件卡的节点附卡片引用。

用节点而不是卡片来排时间线，可以解决“一张卡跨度一整天、把顺序打乱”的问题：一张枚举卡对应几个关键节点（首次、峰值、末次），每个节点都有精确的时间点。

### 4.2 分链

把节点分到不同的链，依据由强到弱：

1. 已登记的 link（同会话、因果、时序）；
2. 共享会话或票据；
3. 共享账号；
4. 共享作用对象（同一配置键、同一菜单）；
5. 仅共享来源地址（只作候选，在图上标为弱关联）。

分链结果由综合 Agent 确认或调整，确认后写入卡片的 `chains` 标注。

### 4.3 断档检测，并生成缺口问题

对每条链按时间检查两类断档：

- **阶段断档**：例如有 credential 和 access，却没有后续的 execution、persistence 或 impact 节点，也没有说明边界的检查；
- **时间断档**：链上相邻两个节点之间存在一段时间，这段时间在覆盖账本里有信号但没有被调查过。

每个断档生成一个**定向的发现问题**，交回发现 Agent，例如“10-05 某时段内，该账号/会话之后是否有执行类行为”。

**这一步就是用路径反向补漏。** 例如，“管理员登录之后没有任何节点”加上“晚间时段有写入信号但无覆盖”，会直接把被漏掉的命令执行阶段送回发现 Agent 去查。

### 4.4 报告第 3 章

1. **攻击路径**：每条链一张 Mermaid 图。节点按时间排列、标注阶段；有证据的关联画实线，推断画虚线，仅时间相邻画点线，断档画灰色节点。
2. **全量时间线**：全部节点按时间排序，包括失败尝试，并标注结果。
3. **外围活动**：未进入任何主链的节点，按系统汇总。

## 5. 子 Agent 的任务侧重

| 角色 | 侧重 | 输入 | 输出 | 不做什么 |
|---|---|---|---|---|
| `ir-prepare` | 入库、**系统分组**、跑确定性摸底 | 原始日志 | 数据集、系统映射、信号 | 不研判 |
| **`ir-discover`（新）** | **找全节点**：研判信号，顺藤找一跳邻居 | 一个系统 × 时间窗，或一组信号，或一个缺口问题 | 节点（批量）、覆盖检查 | 不评估影响、不做来源归属、不写事件卡 |
| `ir-analyze`（由 investigate 改名） | **深挖关键节点**：结果核实、跨日志关联、影响、来源 | 一条链或一组关键节点 | 事件卡、关系、检查 | 不扩大到链外的新广度调查（发现新方向时登记为缺口问题） |
| `ir-synthesize` | **先确认路径，再复核路径上的卡片** | 全部链、卡片、覆盖账本 | 路径确认、复核结论、报告 | 不复核路径之外的每一张卡 |

### 5.1 发现 Agent 的工作方式

按**系统 × 时间窗**或**信号簇**分派，可以并行 3–4 个。每个任务的流程：

1. 读该范围内的信号，逐个判断：真实行为 → 提交节点；噪声 → 提交一条检查，说明排除依据。
2. 对每个新节点**只找一跳邻居**：同会话、同账号、同对象，在前后时间窗内还做了什么。找到即提交节点。
3. 不追第二跳。第二跳由组装阶段发现断档后再派发，避免单个任务无限深入。
4. 任务结束时，覆盖账本里该范围的信号应全部被解释（节点或检查）。

### 5.2 分析 Agent 的工作方式

按链分派，而不是按日志层分派。一个分析任务拿到一条链上的全部节点，以及该链涉及的**全部系统的数据集**。这样请求和应用结果自然落在同一个任务里，能够关联起来。

只对以下节点升级为事件卡：

- 链上阶段为 access / credential / execution / persistence / exfil / impact 的节点；
- 同行结果显示成功、或结果不明但处于关键阶段的节点。

已确认失败的尝试，在链上保留为节点即可，不升级为卡片，也不深挖。

### 5.3 预算分配

| 阶段 | 预算 | 说明 |
|---|---:|---|
| 准备 + 摸底 | 10% | 摸底是确定性代码，几乎不耗模型预算 |
| 发现（含缺口回补） | 40% | 广度优先 |
| 分析 | 30% | 只对路径上的关键节点 |
| 综合 | 20% | 只复核路径 |

## 6. 验证场景

用可公开的测试日志核对三类场景：低频状态变化能否被发现、登入后的操作能否关联原始证据、来源覆盖缺口能否在交付前显式记录。

## 7. 客观评估：风险与代价

| 风险 | 说明 | 应对 |
|---|---|---|
| 节点爆炸 | 发现成本降低后，节点可能过多 | `dedupe_key` 自动合并；节点由信号驱动；每个发现任务设节点上限，超出时要求先聚合 |
| 发现阶段误判严重度 | 不评估影响，可能把关键节点当作外围 | 用阶段猜测和同行结果做粗排序；断档检测兜底 |
| 对象种类变多 | 新增 signal、node 两种对象 | 节点比现有卡片简单得多；事件卡数量会减少，总体流程反而变短 |
| 分链错误 | 仅凭来源地址分链会误合并 | 来源只作弱关联、单独标注；分链由综合 Agent 确认 |
| 旧案件兼容 | 历史案件只有卡片 | 卡片也可以直接作为节点参与排序和分链，旧报告照常渲染 |
| 证据纪律是否被削弱 | 节点更轻 | 节点仍必须钉在原始行上，且字段由工具从原始行抽取，比模型手填更可靠；成功、影响等结论仍只能出现在事件卡上 |

## 8. 实施顺序

每一步都可以单独上线、单独验证：

| 步骤 | 内容 | 主要改动 | 估计 |
|---|---|---|---|
| 1 | **路径标注 + 时间线/路径渲染**（先基于现有卡片） | `events.py` 增加 key_time、stage/chains/outcome 标注且不计入事实哈希；`report_template.py` 重写第 3 章 | 2 天 |
| 2 | **节点对象 + 批量提交 + 自动抽取字段** | `store`/`board` 新增 node；`submit_nodes`；时间线改为以节点为主 | 2–3 天 |
| 3 | **系统分组 + 确定性摸底（信号）+ 覆盖账本** | `ir-prepare` 增加系统映射；新增状态变化/稀有异常/写请求摸底；覆盖账本与结案门槛 | 3–4 天 |
| 4 | **角色拆分**：`ir-discover` / `ir-analyze`，提示词按新职责重写并精简 | `templates.py`；主 Agent 流程 | 2 天 |
| 5 | **组装与断档检测，生成缺口问题** | 新增组装模块；`event_queue` 接入断档问题；综合只复核路径 | 2–3 天 |
| 6 | 来源基线自动生成、生命周期报错自动处理 | `events.py`、`board.py`、`verification.py` | 2 天 |

先做步骤 1，因为它不改变调查流程，就能立刻改善报告的可读性，并为后续步骤提供标注字段。步骤 2–5 构成“节点发现优先”的主体，建议连续完成后用脱敏样本或合成数据做一次完整回归。

**验收指标**包括：

- 节点数 / 事件卡数的比例（期望节点明显多于卡片）；
- 链上阶段断档数，以及其中被回补的比例。
