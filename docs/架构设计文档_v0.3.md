# 应急响应日志分析 Agent 架构设计 v0.3

> 日期：2026-11-13
> 定位：第一版可落地的“分析师主导、Agent 协同”的调查系统。
> 首个验证案件：某业务系统，以 nginx JSON 日志为主。
> 首批日志类型：nginx、Java 应用日志、云审计日志、Windows 导出日志。
> 交付格式：Markdown。

---

## 1. 设计结论

本系统不规定所有案件都经过同一套采集流程，而是采用：

1. **按场景选择采集 Skill**：只有日志、可 SSH 登录实例、已有镜像/挂载盘、持有云 AK/SK 等场景分别处理，可以组合，也可以都不使用而直接导入文件。
2. **统一日志数据库是唯一的必经环节**：无论数据来自哪里，最终都转换为统一事件模型，进入 DuckDB，支持跨日志查询、排序、聚合和实体关联。
3. **事件背景 Brief 是调查起点**：记录分析师已经知道或怀疑的情况，为 Agent 提供初始方向，但不把背景直接当成已证实事实。
4. **Fact 是已定性的事件节点**：调查从锚点开始，对关键节点定性，再逐步寻找它的前一个节点，直到入口或数据边界。
5. **调查顺序和事件顺序分开**：实际调查通常由新到旧；存储的攻击链则统一由旧到新，最终用于生成时间线和报告。
6. **报告由结构化状态生成**：Fact、关系、证据、IOC 和缺口保存在案件状态中，Markdown 报告是渲染结果，不单独维护另一份事实。
7. **第一版采用协同模式**：分析师控制方向和关键定性，Agent 负责查询、关联、重复排查和草稿生成，不追求一开始就全自动调查。

## 2. 系统边界

### 2.1 第一版要解决的问题

- 多来源、不同格式的日志统一查询。
- 大日志文件流式入库，避免反复全量 grep。
- 以 IP、账号、主机、请求、会话、资源等实体进行关联。
- 保存关键事件节点的定性、证据和前后关系。
- 支持从结果向前寻找原因，并在找到入口后向后补全影响范围。
- 明确区分“已证实、疑似、无法判断”，记录日志覆盖不足的地方。
- 从同一份案件状态重复生成 Markdown 报告。

### 2.2 第一版不做

- 自动处置、封禁、隔离或修改客户环境。
- 要求所有案件都具备 SSH、云平台凭据或主机镜像。
- 多人实时共同编辑同一案件。
- 完全自动决定最终入口、影响范围和对外口径。
- 为每种日志建立大量彼此割裂的专用数据库。

## 3. 总体架构

```text
┌──────────────────── 可选的场景 Skill ────────────────────┐
│ 日志包导入 │ SSH 只读采集 │ 云凭据采集 │（镜像/挂载盘：待定）│
└──────────────────────────┬───────────────────────────────┘
                           │ 原始文件 + 来源清单
                           ▼
┌──────────────────── 必选的统一入库层 ────────────────────┐
│ 文件登记与哈希 │ 格式识别 │ 类型解析器 │ 字段归一化        │
│ 时间统一       │ 数据体检 │ DuckDB 批量写入               │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌──────────────────── 统一查询与调查工具 ──────────────────┐
│ SQL │ 时间线 │ 实体关联 │ 单条证据 │ 解码 │ 覆盖范围查询    │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌──────────────────── 协同调查层 ──────────────────────────┐
│ Brief │ 锚点 │ Fact 节点 │ 前向/倒叙任务 │ 证据校验       │
│ 分析师裁定 │ 假设与缺口 │ SQLite 案件状态                  │
└──────────────────────────┬───────────────────────────────┘
                           ▼
┌──────────────────── Markdown 交付层 ─────────────────────┐
│ 概述 │ 数据范围 │ 入口与链路 │ 时间线 │ 影响 │ IOC │ 证据索引 │
└──────────────────────────────────────────────────────────┘
```

建议实现为一个 Claude Code 插件加一个本地工具包：

- **Skills**：保存场景操作说明、调查方法和报告规则。
- **`irkit` CLI/MCP**：负责入库、查询、状态和报告，不让 Agent 重复编写一次性脚本。
- **案件目录**：保存原始证据、数据库、状态和交付物。

## 4. 场景化 Skill

### 4.1 共同约定

每个场景 Skill 只负责“如何取得并登记数据”，不负责最终调查。输出统一为：

```text
case/raw/<source-name>/       原始文件，只读保存
case/manifests/<source>.json  来源、采集方式、时间范围、过滤条件、哈希
```

因此场景 Skill 可以独立演进，也不会影响后续统一查询。

### 4.2 日志包场景

适用于客户直接提供压缩包或日志文件。

- 识别压缩格式、编码和日志类型。
- 保留原始文件，不在原件上修改。
- 记录来源说明：提供人、导出时间、导出条件、是否经过筛选。
- 文件名中的日期只作为辅助信息，以日志内容为准。

### 4.3 SSH 实例场景

适用于获得只读调查授权的实例。

- 采集范围由清单驱动，避免无目的遍历整台主机。
- 先识别实际系统根目录，避免把救援系统或采集机自身日志当成受害数据。
- 只执行读取操作，分块传回并校验哈希。
- 凭据由环境变量或本地凭据工具托管，不写入命令、日志和报告。

### 4.4 镜像或挂载盘场景（待定，第一版不实现）

暂不在第一版实现镜像、快照和救援模式挂载盘采集。未来如确认需要，可作为独立 Acquisition 插件加入，复用相同的原始文件登记、Manifest 和统一入库接口，不改变调查与报告架构。

### 4.5 云凭据场景

适用于通过云平台 API 获取审计日志和资产信息的案件。

- 优先按已知身份、时间窗和事件类型定向采集，再决定是否扩大范围。
- 连接器统一处理分页、限流、时间切片、重试和断点续采。
- 同时采集必要的资产快照，用于解释 IP、实例、网络和账号之间的关系。
- 明确定义采集窗口，防止把“未拉到”误判为“未发生”。

## 5. 统一日志数据库

### 5.1 为什么使用 DuckDB

第一版日志库使用 DuckDB：

- 单文件、嵌入式，适合现场和单案件分析。
- 适合时间窗过滤、分组统计、Top N 和大表扫描。
- 可以直接读取部分 JSON、CSV 和 Parquet 数据。
- 某业务系统约 39GB 的日志可作为首版性能验证。

入库必须采用流式读取和批量写入，不能把整个文件加载进内存。

### 5.2 统一事件模型

不追求把所有日志字段强行塞进几十列，而是采用“公共字段 + 原始属性”的方式：

```sql
CREATE TABLE evidence_files (
    file_id         VARCHAR PRIMARY KEY,
    source_name     VARCHAR,
    original_path   VARCHAR,
    stored_path     VARCHAR,
    sha256          VARCHAR,
    size_bytes      BIGINT,
    source_type     VARCHAR,
    acquired_at     TIMESTAMP,
    metadata_json   JSON
);

CREATE TABLE events (
    event_id        VARCHAR PRIMARY KEY,
    file_id         VARCHAR,
    record_ref      VARCHAR,       -- 行号、事件记录号或其他稳定定位信息
    byte_offset     BIGINT,        -- 文本日志可用，便于回查
    ts_utc          TIMESTAMP,     -- 可解析时填写
    ts_original     VARCHAR,       -- 原始时间字符串
    timezone_source VARCHAR,       -- 日志自带、文件配置、人工指定等
    host            VARCHAR,
    environment     VARCHAR,       -- prod/test/uat/unknown
    source_type     VARCHAR,       -- nginx/java_app/cloud_audit/windows
    category        VARCHAR,       -- http/application/cloud/system 等
    action          VARCHAR,       -- 归一化动作
    outcome         VARCHAR,       -- success/failure/unknown 等
    actor           VARCHAR,       -- 账号、云身份或其他主体
    src_ip          VARCHAR,
    dst_ip          VARCHAR,
    object          VARCHAR,       -- URL、资源、文件、服务名等
    summary         VARCHAR,       -- 简短、可展示的摘要
    attributes_json JSON,          -- 该日志类型特有字段
    parse_status    VARCHAR,
    parse_error     VARCHAR
);
```

`event_id` 由案件、文件和记录定位信息稳定生成。同一份原始数据重复入库时，事件编号不能变化。

### 5.3 时间、环境与证据定位

- 所有可解析时间统一转换为 UTC，原始时间和时区来源必须保留。
- 报告展示时再统一转换为目标时区。
- 生产、测试等环境标签尽量由明确规则生成；规则来自分析师确认，而不是仅凭域名猜测。
- 每条事件都能通过 `file_id + record_ref` 回到原始文件。
- 无法解析的行不能静默丢弃，应记录数量和原因。

### 5.4 数据覆盖概览

入库结束后自动生成：

- 每个文件的成功、失败和跳过记录数。
- 每个数据源、主机和环境的最早、最晚时间。
- 按天或按小时的记录数量，发现明显断档。
- 时间字段缺失、时区不明和时钟偏差情况。
- 可能的过滤痕迹，例如只包含单一来源或单一身份。
- 明确不能从该数据源判断的事项。

这些内容用于约束后续结论，而不是只作为技术统计。

## 6. 首批解析器

### 6.1 nginx

- 支持 JSON、常见文本格式及已知的自定义格式。
- 自定义格式优先读取配置定义，不按字段位置猜测。
- 区分直接连接地址、代理地址和原始客户端地址。
- 保留完整 URL、状态码、响应大小、耗时和请求方法。
- 对请求体、认证头等敏感内容设置长度限制和展示脱敏。
- 解码仅作为数据处理，设置大小、层数和耗时上限。

### 6.2 Java 应用日志

- 将时间戳行与后续堆栈行合并为一个逻辑事件。
- 提取级别、线程、logger、异常类型、消息和主要调用位置。
- 有 trace/request 标识时保留，供跨日志关联。
- 明确其能力边界：报错和调用栈通常不能单独证明一次外部操作最终成功。

### 6.3 云审计日志

- 兼容 CSV 中嵌套 JSON 和直接 JSON 两种形式。
- 统一提取身份、动作、资源、来源地址、请求标识和返回信息。
- 将平台特定的结果判断封装为适配规则，避免把“接口已受理”直接当成“动作已完成”。
- 保存采集窗口和查询条件，以判断结论覆盖范围。

### 6.4 Windows 导出日志

- 支持 EVTX 转出的 JSON/XML，以及后续增加的直接 EVTX 解析。
- 保留 Event ID、Record ID、Channel、Provider 和原始字段。
- 将账号、登录标识、进程、服务和网络字段映射到公共模型。
- 不把不同 Windows 事件简单视为同一种动作，具体语义由解析适配器处理。

## 7. 案件状态与核心概念

日志事件放在 DuckDB；调查状态放在同一案件目录下的 SQLite 数据库。两者通过 `event_id` 关联。

### 7.1 Brief：事件背景

Brief 是分析师给 Agent 的初始上下文，例如：

- 已确认是 Web 入口相关事件。
- 已发现某类应用异常。
- 已确认某些云身份存在异常调用。
- 客户关注的起始时间、主机、账号或域名。
- 已确认的生产/测试环境划分。
- 已知的处置动作和时间边界。

Brief 条目应带状态：

- `confirmed_by_human`：分析师或客户确认，可作为调查约束。
- `suspected`：仅为初始思路，需要验证。
- `rejected`：已经否定，保留以防旧结论重新出现。

Brief 不是证据，也不能直接生成 confirmed Fact。

### 7.2 Fact：已定性的事件节点

Fact 不是任意一条日志，而是对调查有意义的事件节点。一个 Fact 应回答：

> 在什么时间，哪个主体，对哪个对象，发生了什么，结果如何，依据是什么？

建议字段：

```text
fact_id
statement             简明陈述
time_start/time_end   事件时间
hosts/entities        相关主机、账号、IP、资源等
verdict               malicious/suspicious/benign/operational/unknown
outcome               attempted/accepted/succeeded/failed/unknown
confidence            confirmed/strong/inferred/unknown
evidence_event_ids    必填，可回查原始日志
status                candidate/confirmed/rejected/superseded
created_by            analyst/agent/task
revision              乐观并发版本号
created_at/updated_at
```

规则：

- `confirmed` 必须有可回查证据。
- 推断可以保存，但必须标为 `inferred`，不能写成确定结论。
- 新证据推翻旧结论时，新增修订或标记 superseded，不物理删除历史。
- 定性错误应容易纠正，并能看到哪些下游结论依赖它。

### 7.3 FactLink：节点之间的关系

FactLink 表示节点之间的关系，不把所有相邻事件都强行解释为因果：

```text
from_fact_id       较早或上游节点
to_fact_id         较晚或下游节点
relation_type      possible_cause/causal/same_session/identity_reuse/time_related
confidence
evidence_event_ids
explanation
```

调查可以从 `to_fact_id` 向前找到 `from_fact_id`，但存储和展示仍按事件发生方向组织。

### 7.4 TraceTask：待查任务

每个任务围绕一个明确问题，而不是“继续分析全部日志”：

```text
task_id
based_on_fact_id
direction          backward/forward/lateral/verify
question
scope              主机、时间窗、数据源和实体
priority
status             open/running/done/blocked/cancelled
result_fact_ids
coverage_note
```

主要类型：

- **backward**：寻找当前节点的前置条件或来源。
- **forward**：入口明确后，补全后续行为和影响。
- **lateral**：检查同一实体在其他主机、账号、数据源中的出现情况。
- **verify**：核实结果等级、证据和结论强度。

### 7.5 Gap 与 Coverage

- **Gap**：某段时间、主机或数据源缺失，导致什么问题无法回答。
- **Coverage**：实际查询过哪些数据源、时间范围和条件，结果是否有命中。

“没有查到”只有附上 Coverage 才有意义；存在 Gap 时不能写成确定的不存在。

## 8. 倒叙调查流程

### 第一步：建立案件与 Brief

记录调查目标、客户现象、已知时间、环境范围和初始判断。分析师可以只提供简短描述，后续持续补充。

### 第二步：按场景采集，统一入库

按需调用场景 Skill。无论是否有额外采集，最终都进入统一数据库并生成数据覆盖概览。

### 第三步：确定锚点

锚点以下来源均可：

- 分析师指定的事件或时间。
- 已知告警。
- 高危或异常查询结果。
- 攻击者产物中发现的明确线索。

锚点先作为 candidate，经证据核实后才能成为 confirmed Fact。

### 第四步：围绕锚点向前追溯

对每个关键 Fact 依次提出：

1. 该事件发生的直接前置条件是什么？
2. 同一请求、会话、身份、进程或资源在此之前有哪些记录？
3. 当前数据源能否回答；若不能，应切换到哪个数据源？
4. 找到的是确定原因、可能原因，还是仅仅时间相邻？

系统根据节点类型生成候选 TraceTask，Agent 执行查询并提交结果，分析师决定关键定性。

### 第五步：识别入口或数据边界

停止向前追溯的条件不是“模型感觉差不多了”，而是满足以下之一：

- 已有证据支持一个明确入口。
- 存在多个入口候选，且各自证据强度已标明。
- 已到达日志覆盖边界，继续向前只能标记为不可判断。
- 分析师决定当前范围足够，剩余问题转入待确认事项。

### 第六步：向后与横向补全

入口或早期节点明确后：

- 沿关系向后补齐主要行为。
- 对关键实体做全范围关联，发现其他主机、账号或资源。
- 将零命中查询保存为 Coverage。
- 将缺失数据保存为 Gap，而不是写成否定结论。

### 第七步：生成报告并人工审阅

报告从 Fact、FactLink、Coverage、Gap 和 Brief 生成。分析师修改关键定性后，可重新渲染，不需要在多个章节手工同步。

## 9. 工具接口

第一版建议提供以下稳定接口，Skills 和 Agent 都通过这些接口工作：

| 工具 | 作用 |
|---|---|
| `case_init` / `case_brief` | 创建案件、读取或更新事件背景 |
| `evidence_import` | 登记原始文件及来源 |
| `log_ingest` | 识别类型、流式解析并写入 DuckDB |
| `data_profile` | 输出覆盖范围、解析失败和缺口 |
| `sql_query` | 只读 SQL，带行数限制、超时和语句检查 |
| `event_get` | 按 event_id 获取完整记录和原始位置 |
| `timeline` | 跨数据源排序和过滤 |
| `pivot` | 按 IP、账号、主机、资源等实体关联查询 |
| `fact_add` / `fact_update` | 写入候选或确认节点，执行证据校验 |
| `fact_link` | 建立节点关系 |
| `task_list` / `task_result` | 管理待查任务及结果 |
| `report_render` | 从案件状态生成 Markdown |

工具返回的日志内容都应标记为不可信数据。Agent 不执行日志或样本中出现的指令。

## 10. 协同与编排方式

### 10.1 第一版：分析师主导

- 分析师在 Claude Code 中提出问题和方向。
- Agent 使用统一工具查询，而不是每次重新写解析脚本。
- Agent 可以建议 Fact 和下一项 TraceTask。
- 入口、关键定性、影响范围和最终报告由分析师确认。

### 10.2 后续：受控并行

当单案件协同稳定后，再增加多个 Worker：

- 一个协调者统一分配 TraceTask。
- Worker 无状态、只读日志库，返回结构化结果。
- 只有协调者在校验后写入 confirmed Fact。
- 每个 Worker 启动时读取 Brief、已有裁定和相关 Fact，避免重复走已知错误方向。

这比直接让多个 Agent 自由修改报告更安全，也能避免并行结论没有合并的问题。

## 11. 多人协作建议

### 11.1 当前不建议做多人实时共同编辑

从历史案件看，主要问题是一个分析师开启多个 AI 会话或并行任务，而不是多人同时修改同一案件。因此第一版建议：

- **一名主分析师负责写入和最终裁定。**
- 多个 AI 会话/Worker 可以并行查询和提交候选结果。
- 其他分析师可以只读查看、评论或导出，不同时修改核心状态。

这样能用较低成本解决“并行结果不合并”和“纠正后旧结论复活”的问题。

### 11.2 架构上保留升级空间

当前单机实现：

- DuckDB：入库单写者，调查阶段只读查询。
- SQLite WAL：允许多个本地会话访问状态，但写入统一经过 `irkit`。
- 状态带 `revision`、`created_by` 和时间，重要变化采用追加修订。
- 所有派生报告可重建，不成为第二份事实来源。

未来确有跨机器多人协作需求时，可升级为：

- 中央 Case API 服务。
- PostgreSQL 保存案件状态。
- ClickHouse 保存集中日志。
- 对象存储保存原始证据。

Skills 和调查工具只依赖稳定接口，因此不需要因数据库替换而重新设计调查方法。

## 12. Markdown 报告

建议固定骨架：

```markdown
# 应急响应报告

## 1. 事件概述
## 2. 调查范围与事件背景
## 3. 数据源、时间覆盖与局限
## 4. 入口及主要结论
## 5. 攻击事件时间线
## 6. 事件链路与关键证据
## 7. 受影响主机、账号与资源
## 8. IOC 与排查清单
## 9. 未决问题与数据缺口
## 10. 处置和加固建议
## 附录：证据文件与哈希
```

生成规则：

- 时间线由 Fact 按时间排序生成。
- 事件链可由 Mermaid 表达，不能确认的关系使用虚线并标注。
- 数字尽量由查询或命名统计生成，不在多处手工填写。
- 每个关键结论附 Fact ID 和证据索引。
- 报告正文可以人工润色，但结构化事实仍回写状态库，避免下次渲染丢失修改。

## 13. 安全与可靠性

- 原始证据只读保存并记录哈希。
- 查询接口只允许只读操作，限制执行时间、返回行数和敏感字段展示。
- 云凭据和 SSH 凭据集中托管，不进入提示词、命令文本和交付物。
- 日志、请求参数、异常消息和样本内容均视为不可信数据，防止提示注入。
- 解码和静态提取设置资源上限，不执行未知文件。
- 所有 Agent 写入保留作者、时间和证据，支持审计和撤回。
- 结论强度不得超过证据强度；数据缺失必须显式表达。

## 14. 分阶段实施

### P0：某业务系统最小闭环

目标是先跑通“统一入库—查询—Fact—Markdown”：

1. 案件目录与 SQLite 状态。
2. 日志包导入和 nginx JSON 流式解析。
3. DuckDB 统一事件表、数据覆盖概览。
4. `sql_query`、`timeline`、`pivot`、`event_get`。
5. Brief、Fact、FactLink、TraceTask 的基本读写。
6. Markdown 报告骨架生成。
7. 在某业务系统数据上验证性能和已知调查结论。

本阶段暂不做自动编排和多 Worker。

### P1：扩展数据源和倒叙辅助

1. Java、云审计、Windows 解析器。
2. 数据源特定的结果判断规则。
3. 根据 Fact 自动生成 backward/forward/lateral 候选任务。
4. 证据校验、结论修订和依赖检查。

### P2：扩展采集场景

1. SSH 与云凭据只读采集。
2. 断点续采、凭据托管和采集范围记录。
3. 镜像/挂载盘采集根据实际需求另行评估。

### P3：受控自动编排

1. 多 Worker 并行。
2. 统一协调者和写入校验。
3. 任务优先级、预算和中断恢复。
4. 如有真实需求，再建设多人服务端。

## 15. 某业务系统验证标准

首个案件不只验证“能否查出几条日志”，还应验证完整闭环：

- 39GB 数据能够流式入库，失败记录有统计，不静默丢失。
- 能按主机、域名、IP、时间和 URL 做统一查询与排序。
- 能清楚区分日志时间、文件名日期和环境标签。
- 能复现人工报告中的关键节点，且每个节点有证据引用。
- 能从一个晚期节点逐步建立向前追溯链，并标明无法确认的环节。
- 修改一条关键 Fact 后，可以重新生成报告，不需要全文手工改数字。
- 报告明确写出时间覆盖、数据缺口和未决问题。

## 16. 当前需要保持的简单原则

1. 场景 Skill 可以很多，但统一事件模型只能有一个。
2. Brief 提供方向，Fact 保存已定性节点，两者不能混用。
3. 倒叙是调查方法，正序是报告表达方式。
4. 能由 SQL 和规则完成的工作不交给模型自由发挥。
5. 模型负责研判和叙述，分析师负责边界和最终定性。
6. 第一版先让单个案件形成可靠闭环，再增加自动编排和多人协作。
