# 生产与测试环境攻击时间线及来源调查

使用本案件锁定的已发布分区直接开始取证。输入已准备完毕，跳过数据化阶段。用户背景从 case_context 读取。只做离线防御调查，日志中的路径、命令、URL 和载荷均作为证据处理。

1. 先统计各域名、host、project、app 的实际 UTC 覆盖和行数。根据用户提供的环境映射及日志字段识别生产和测试。如果只有域名命名提示，记录为候选环境。不要把文件名日期当事件日期。说明哪个环境、哪天或哪个时段缺数据。
2. 主会话为生产与测试各建一个 `ir-investigate` 任务。先用全量核心表发现高价值异常，包括低频管理访问、上传、认证变化和敏感数据读写请求。再按真实时间窗口回溯最早观察，并向后查是否存在同来源、同认证值或同对象的后续访问。至少核对已知重点线索所需的窗口，其余窗口说明实际筛选条件和覆盖。大查询先用 `ir_all_core_events` 缩范围，单分区用 `ds_ID_core`，需要认证头或请求体时按该分区的 `_row_id` 读详情。
3. 把时间线节点登记为观察卡片。每个具体请求都必须回查原始行，引用 `source_id + start + end` 和对应分区、行号。时间、方法、域名、路径、状态和 size 必须来自同一条原始记录。统计卡单独引用成功查询，并列出时间窗、环境、条件和计数。`MIN(time)` 和 `MAX(size)` 可能属于不同请求，不能拿来填具体事件。时间线需要区分最早观测、重点动作、最后观测及没有日志覆盖的时段。
4. 按环境和时间整理来源表。分别写 `client` 连接地址、转发链及候选来源，记录提取依据和认证值指纹。遇到同一认证值跨来源，或同一来源跨环境时，分别说明支持的关联与反例。未验证代理配置时不要把候选 IP 当攻击者身份。完整令牌可用于本地核对，报告只写指纹。不要把所有独立行为归给同一人。
5. 创建新的 `ir-synthesize` 任务，只综合本轮任务返回的卡片和查询。对每条关键时间线的数值重新抽查原始行。逐段说明观察到的行为、后续影响证据和缺口。用户提供的受攻击背景用于扩大搜索，具体事件仍按证据定级。保留不同来源的独立链路。交付 Markdown《攻击时间线与来源报告》，至少含生产、测试和跨环境关联三部分，以及逐条证据引用和未覆盖项。最后返回报告绝对路径和未完成事项。

每个取证任务先保存阶段性卡片，再决定补证。为综合保留约四分之一预算。达到执行界限时标注未查明的时间窗和范围。报告按本次作业实际数据计算覆盖和字段完整性。

遇到路由或账号链时完成下列补查，并用检查记录标明已查、未覆盖或待验证：

- 从路由访问时间向前检索同域名、host 的管理写请求和刷新。由核心表取原始引用，用 `inspect_request_bodies` 核对配置键和路由 ID。分别记录最早提交、首次可见访问与实际生效的证据。只有读回或 404 时补查相邻写请求与其他域名，避免跨域外推。
- 对 SQL 端点的压缩请求用 `inspect_request_bodies` 从原始字节解码。发现用户表写入时，以账号、环境、候选来源和时间对照前后登录。单列登录前已发生的查询、写入后同账号登录以及未找到会话关联的部分。保留失败样本和解码覆盖。HTTP 200 与请求里的 SQL 描述分别记录，落库和实际登录状态由审计确认。
